## 一、通道选型的实测结论（这决定了架构）

| 候选通道 | 实测结果 | 结论 |
|---|---|---|
| ColorOS 短信直发 | 第三方 App 发短信**逐条弹系统确认框**（`Permission Intercept`），不点即拒；`cmd role add-role-holder android.app.role.SMS` 被系统拒（未声明默认短信应用组件） | **不可用**（除非接管整个短信应用，风险高且不保证生效） |
| 局域网 HTTP 直推 | 两端都已实现（副端 webhook + 主端 8788 监听），单机回环实测 `{"ok":true,"got":1}` | 可用，但**要求两台机同一 Wi-Fi** |
| `ntfy.sh` / `broker.emqx.io` | 两台手机 **ping 不通**（国内网络） | 排除 |
| `api.day.app`(Bark) / `sctapi.ftqq.com`(Server酱) / `qyapi.weixin.qq.com` | 可达 | 只发不拉，主端无法取；且经第三方 | 排除（主端需可轮询） |
| `api2.pushdeer.com` | 可达（`/message/push` 返回「错误的Key」=服务在跑），有 `/message/list` 可拉 | 可用，但要从 PushDeer 客户端拿 pushkey（多装一个 App） | 备选 |
| **邮箱（SMTP 发 + POP3 拉）** | `smtp.qq.com` / `imap.qq.com` 两台机都可达；离线用 PC 上的模拟 SMTP+POP3 **端到端验通** | **采用**（不经第三方服务器、任何网络都通） |

## 三、邮箱通道的端到端证据（离线验，用 PC 上的模拟 SMTP+POP3）

| 环节 | 原始读数 |
|---|---|
| 副端发送 | `16:04:27 已转发 #2 via email：已发邮件到 te***@local` |
| 模拟服务器收信 | `16:07:52 SMTP: 收到一封信，共 1 封` |
| 主端取信 | `16:07:59 POP3: 取走 uid3` |
| 主端落库 | `#5 16:07:59 [sms] SIM? 10086 code=112233` |
| 主端链路日志 | `邮箱通道取回 1 封` → `收到验证码 [sms] code=112233 来自=10086` → `已弹通知：验证码 112233` |

> 离线验证的价值：把「SMTP 客户端 / POP3 客户端 / base64 正文 / UIDL 去重 / 前缀解析」这些最容易写错的部分先钉死，再换真邮箱，避免把协议 bug 误判成「邮箱服务商问题」。

## 三之二、真机端到端（2026-10-14 实跑，最要紧的一条）

| 环节 | 原始读数 |
|---|---|
| 副机收到真短信 | 由主机号码 `+8613xxxxxxxxx` 发到副机 |
| 副端转发 | 状态页 `通道：email → 27***@qq.com → 自己`；`近 24h：收 1 / 转 1` |
| 邮箱 | 用户在 QQ 邮箱里确认收到主题形如「[转发]SIM1 +86… 验证码 995511」的自己的来信 |
| 主端落库并展示 | 主端状态页 `近 24h 收到 1 条；最后一条 995511（26 秒前）`；横幅通知「验证码 995511 / SIM1(中国移动) +8613xxxxxxxxx / [复制验证码]」 |

> 时延口径：主端每 20 秒轮询一次（可调 5~600 秒），所以从副机收到短信到主机可见，实测在 **一次轮询周期内**（本次 26 秒内）。若要更快把间隔调到 5~10 秒即可。

## 三之三、一个必须记下的教训（已修）

初版 POP3 轮询把**所有取到的邮件**在「不是转发格式」分支里也执行了 `DELE`——等于把用户邮箱里的其他来信（GitHub / OpenAI / SendGrid 通知等）一并删掉。判定依据是主端日志里成片的 `邮件不是转发格式，跳过：主题: Received from …`。

**修法**：只有确认是我们自己发出的那封（正文以 `[转发]` 开头）才 `DELE`；其余一律「只记 UIDL 见过、绝不删除」。日志文案也改成明确的「非转发邮件，跳过（不删）：<主题>」。

**通用规矩**：任何「拉取并消费」的通道，删除动作只能作用于自己产生的数据；对用户已有数据的默认动作必须是「不动」。

## 四、本次踩到并修掉的坑

| # | 坑 | 判据 / 现象 | 修法 |
|---|---|---|---|
| 1 | `createSocket(host, port)` 的 connect 无超时 | 对端黑洞化时轮询线程**永久阻塞且零报错**（日志停在某一行） | 先 `Socket().connect(addr, 8000)` 再包 SSL |
| 2 | 新装 App 处于 stopped 状态 | `am broadcast` 打不进 debug 接收器，且无任何报错 | 先 `am start` 启动一次 |
| 3 | `SSLSocketFactory.getDefault()` 静态类型是 `SocketFactory` | 4 参数 `createSocket` 编译不过 | 显式 `as SSLSocketFactory` |
| 4 | ColorOS 安装通道卡死 | install session `committed` 但永不 `applied`，界面「安装失败」 | 改用手机端侧载；adb 通道不可靠 |
| 5 | 两端 ROM 都拦「广播唤醒未运行的 App」 | `OplusAppStartupManager: sikp broadcast…proc does not exist` | 靠前台服务常驻 + 开机自启 + ROM 白名单 |
| 6 | 副端状态行看错字段 | `sms` 通道下显示 webhook 地址（永远空）→ 用户以为「保存没生效」 | 通道自检函数按通道显示对应字段 |
